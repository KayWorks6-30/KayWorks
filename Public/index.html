About

Why I make these.

I like making software in my free time. Most projects start with something pretty ordinary: I want a better way to keep track of something, an existing app is doing way more than I need, or I think a small annoyance could be handled better.

Once one of those projects gets useful enough, I clean it up and keep it here. The point is not to turn every idea into a product. I just like making things that work well and letting other people use them if they happen to fit what they need.

I tend to prefer apps that open quickly, explain themselves, and do not make you create an account unless there is a real reason for one. If data can stay on your device and still do the job, that is usually where I want it.

The basic idea

  • Keep the app easy to understand.
  • Do not add setup just because other apps do.
  • Let local data stay local when it makes sense.
  • Add complexity only when it actually helps.

KayWorks is just the name I use to keep all of these projects together.

Technical

How the apps work.

There is real structure behind the projects, but the basic idea is simple: use the lightest setup that can do the job reliably.

From the user side

The technical choices mostly exist so the app can stay easy to use.

No account unless it is needed

Most KayWorks apps do not need a KayWorks login. If an app can remember its own state locally, I would rather leave it at that.

Local-first data

Where it makes sense, personal data stays in browser storage on your device instead of being sent to a central KayWorks database.

Backups matter

Local data can still be lost if browser storage is cleared or a device disappears. Apps with meaningful history should give you a way to export and restore it.

Local-first is a design choice, not a magic security claim.

Your data staying on your device avoids building one big database of everyone’s information. It does not make the data invulnerable, which is why backups are important.

Under the hood

Money Tracker is the first KayWorks app big enough to need a more formal structure.

Keep the layers understandable

UI code should deal with the interface. Financial or other domain logic should work without depending on the screen. Storage should have a clear boundary instead of being scattered everywhere.

UI→domain / data→persistence

AI interprets; the app decides

AI can be useful for turning messy text into structured input. Important calculations and stored behavior should still be validated and handled deterministically by the application.

input→AI / parser→validation→app logic

Static is fine

HTML, CSS, JavaScript, browser APIs, and static hosting cover a surprising amount. I do not add a backend or framework just so the project looks more “serious.”

Structure should match the app

A tiny utility should stay tiny. A larger app can grow data, domain, parser, UI, test, and release layers when those boundaries actually make the project easier to maintain.
